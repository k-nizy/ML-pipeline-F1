## 2.1 Design goals

The dataset is a single time series with one target (hourly PM2.5), one monitoring site
and five meteorological covariates, observed 43,824 times between 2010-01-01 and
2014-12-31. Two database systems are implemented over that same data, and the design
brief for each was driven by what the rest of the pipeline has to do with it:

| Requirement | Consequence for the design |
|---|---|
| The "latest record" and "records by date range" endpoints must stay fast as the series grows | Timestamps must be indexed on their own, not only as part of a composite key |
| Re-running the loader must not duplicate rows | A natural uniqueness rule (one sensor, one hour) enforced by the database, used as the upsert key |
| Lags and 7/30-day moving averages are required analytics | A daily rollup table + a window-function view, rather than recomputing over 43k hourly rows per query |
| Task 1's experiment table must be reproducible | Model metadata, run metrics and predictions stored as first-class tables, not notebook output |
| Missing target values must never be mistaken for clean air | `pm25` nullable with an `is_imputed` flag; zero-filling rejected at the schema level |

## 2.2 Relational schema (MySQL 8.0)

Six tables in three layers. The brief asks for a minimum of three; six are used because
the pipeline stores three genuinely different kinds of data — measurements, derived
features, and model provenance — and merging any two would either duplicate the fact
rows or make the required time-range queries unindexable.

**Table 2.1 — Schema overview** (`sql/schema.sql`)

| Table | Layer | Grain | Key columns | Rows loaded |
|---|---|---|---|---|
| `stations` | Dimension | one row per site | `station_id` PK, `UNIQUE(station_name)` | 1 |
| `readings` | Fact | one row per **station-hour** | `reading_id` PK, `UNIQUE(station_id, observed_at)` | **43,824** |
| `daily_aggregates` | Derived | one row per **station-day** | `agg_id` PK, `UNIQUE(station_id, agg_date)` | **1,826** |
| `models` | Model registry | one row per model config | `model_id` PK, `UNIQUE(model_name)` | populated by Task 1 |
| `forecast_runs` | Experiment | one row per training run | `run_id` PK, `UNIQUE(model_id, experiment_label)` | populated by Task 1 |
| `forecast_predictions` | Output | one row per forecasted hour | `prediction_id` PK, `UNIQUE(run_id, target_time)` | populated by Task 4 |

Supporting objects: the view `v_daily_pm25_moving_avg` (lags and moving averages) and
the stored procedure `sp_refresh_daily_aggregates` (rebuilds the rollup from the fact
table, so the derived layer can never drift).

### 2.2.1 Keys and integrity constraints

- **Surrogate primary keys** (`AUTO_INCREMENT`) throughout. Natural keys in time-series
  data are unstable — a station can be renamed, a model retrained — and would be wide to
  carry through every foreign key.
- **`UNIQUE(station_id, observed_at)`** on `readings` encodes the real business rule: one
  physical sensor cannot report two values for the same hour. It doubles as the loader's
  upsert key, which is why `load_mysql.py` is idempotent — re-running it refreshes values
  and leaves the row count at exactly 43,824.
- **`ON DELETE CASCADE`** from `stations` and from `forecast_runs`, so deleting a site or
  an experiment cannot leave orphaned measurements or predictions behind.
- **`CHECK` constraints** on `pm25 >= 0`, `wind_speed >= 0` and the latitude/longitude
  ranges. Sensors fail by reporting nonsense (negative concentrations, impossible
  coordinates) and the database is the last line of defence before that reaches the model.
- **`pm25` is nullable by design.** 2,067 hours (4.7 %) have no reading because the
  instrument was down. Storing `0` would look like perfectly clean air and would bias
  every average and the learner itself; `is_imputed` records the cases where the
  preprocessing step filled a gap so analyses can include or exclude them.

### 2.2.2 Index decisions

| Index | Columns | Serves |
|---|---|---|
| `uq_readings_station_hour` | `(station_id, observed_at)` | duplicate prevention, upsert, per-site time ordering |
| `idx_readings_observed_at` | `observed_at` | the date-range endpoint |
| `idx_readings_pm25` | `pm25` | threshold/anomaly queries (e.g. hours above 300 µg/m³) |

`idx_readings_observed_at` is not redundant with the composite unique key: `station_id`
is that key's leading column, so a predicate on `observed_at` alone cannot use it. The
cost of getting this wrong is measurable — the month-long date-range query in §2.4 reads
**744 of 43,824 rows (1.7 %)** as a range scan instead of scanning the whole table:

```text
type=range  key=idx_readings_observed_at  rows=744  Extra=Using index condition
EXPLAIN ANALYZE: Index range scan ... (cost=335 rows=744) (actual time=0.799..4.45 rows=744 loops=1)
```

The composite key also serves a second job: because it is ordered `(station_id,
observed_at)`, "latest record for this station" is an index lookup rather than a sort.

### 2.2.3 Why `daily_aggregates` is deliberately denormalised

In strict 3NF this table is redundant — every column can be recomputed from `readings`.
It is kept for three reasons:

1. **The required analytics are lag and moving-average based.** A 7-day moving average
   over 1,826 daily rows is cheap; the same window over 43,824 hourly rows, repeated for
   each analytical question, is not.
2. **Hourly PM2.5 is too noisy to show a daily trend.** A 7-day mean of hourly values is
   dominated by the day/night cycle; a mean of daily means answers "is the air getting
   worse?" directly (Figure 2.4).
3. **Data quality travels with the aggregate.** `pm25_count` records how many hours
   actually had a value, so any downstream query can exclude incomplete days. 37 whole
   days have `pm25_count = 0` and store `NULL` rather than a mean computed from nothing.

The view `v_daily_pm25_moving_avg` exposes `pm25_lag1`, `pm25_lag7`, `pm25_ma7`,
`pm25_ma30` and `ma7_window_days`. The final column matters: the first six days of the
series have partial 7-day windows, and surfacing the window length is more honest than
silently averaging over fewer days.

## 2.3 Queries performed (SQL)

Seven queries are implemented; the brief requires three. All are in
[`../sql/queries.sql`](../sql/queries.sql) and their full output in
[`../outputs/query_results.md`](../outputs/query_results.md). Each figure below is an
unmodified MySQL Workbench result grid for the statement of the same number.

**Table 2.2 — SQL queries, purpose and result**

| # | Question answered | Technique | Result | Evidence |
|---|---|---|---|---|
| Q1 | What is the most recent observation? | `ROW_NUMBER()` partitioned by station | 1 row: 2014-12-31 23:00, PM2.5 = 12 µg/m³, NW 249.85 m/s | Figure 2.2 |
| Q2 | Value yesterday, last week, and its 7/30-day averages | view with `LAG()` + windowed `AVG()` | 14 rows; e.g. 2014-12-31 avg 10.04 vs MA7 121.20 | Figure 2.3 |
| Q3 | Which months are worst? | `GROUP BY YEAR(), MONTH()` | 60 rows; worst = Jan 2013 at 194.2 µg/m³ mean, 27 days above 150 | Figure 2.4 |
| Q4 | Is there a 1-day lag effect? | Pearson r computed inline in SQL | **r = 0.5632** over 1,770 paired days | Figure 2.5 |
| Q5 | Do external variables relate to the target? | `GROUP BY wind_dir` with `AVG/MAX/STDDEV_SAMP` | calm/variable 126.2, SE 110.8, NE 90.2, NW 70.1 µg/m³ | Figure 2.6 |
| Q6 | Worst hours inside a date range | `BETWEEN` on `observed_at` + `pm25 >= 300`, joined to `stations` | 20 rows; peak 671 µg/m³ on 2014-01-16 04:00 | Figure 2.7 |
| Q7 | How do the trained experiments compare? | join `forecast_runs` → `models` | the Task 1 experiment table, ordered by RMSE | Figure 2.8 |

Findings that matter for the modelling task:

- **Q1** returns exactly one row even though the query is written for many stations — the
  design is multi-site ready, which is why the endpoint is not `ORDER BY ... LIMIT 1`.
- **Q2** shows the daily series swing from 10 µg/m³ to 239 µg/m³ inside two weeks while
  the 30-day mean stays near 85 µg/m³: the volatility is short-term, sitting on a stable
  seasonal baseline. This is the direct justification for the lag and rolling features
  used in Task 1.
- **Q3** puts six of the fifteen worst months in November–February, confirming the
  heating-season pattern; summer months never reach the top of the list.
- **Q4** gives a **moderate positive lag-1 correlation (0.5632)** — yesterday explains a
  meaningful but not dominant share of today's variance, so lag features carry real
  information and a naive "tomorrow equals today" forecast would still lose a lot of
  accuracy. Both facts appear again in the model's experiment table.
- **Q5** is the clearest external relationship in the data: calm or variable winds average
  126.2 µg/m³ while north-westerly winds average 70.1 — a 56 µg/m³ gap consistent with
  the physical mechanism (stagnant air traps pollution; NW flow ventilates the basin). The
  column is a 17-value `ENUM` even though only four values occur in the data, so a future
  feed that reports, say, `WNW` loads without a migration.
- **Q6** shows a single severe episode (16 Jan 2014, 00:00–12:00) accounting for most of
  the month's extreme hours — pollution events are episodic, not gradual.

## 2.4 MongoDB collection design

The document model stores one document per station-hour, mirroring the `readings` fact
table with the flat row grouped into meaningful sub-documents (`station`, `target`,
`weather`), and is indexed on `timestamp` plus a unique `(station.id, timestamp)` to
match the two relational access paths. Collection definition, sample documents and the
required queries are covered in the MongoDB subsection (§2.5) and in
[`../mongodb/`](../mongodb/).

The deliberate contrast is worth stating: the relational schema normalises the site out
into `stations` because SQL joins are cheap and the dimension may grow; MongoDB embeds a
short station summary in every document because the API reads one hour at a time and a
document-per-hour with the station inline answers "latest record" and "this range" in a
single read. Both systems keep the same uniqueness rule, which is what makes the two APIs
interchangeable behind the same FastAPI service.

## 2.5 Limitations of the database layer

- **Timezone**: timestamps are stored exactly as published (Asia/Shanghai) without an
  offset, so `TIME_ZONE` is a deployment concern. Mixing in UTC data would shift every
  lag by 8 hours; this is flagged rather than silently converted.
- **One station**: the dataset is a single site, so `stations` holds one row. Every query
  is written to survive multiple stations (Q1 partitions, Q3 groups), but no cross-station
  comparison is possible with this data.
- **Spatial mismatch**: PM2.5 is measured at the US Embassy monitor while the weather
  columns come from Beijing Capital Airport ~20 km away. This is inherent to the source
  and is documented in the schema and the loader rather than hidden.
- **The model tables are validated, not yet populated**: `models`, `forecast_runs` and
  `forecast_predictions` are exercised by Q7 and by the prediction script, but contain
  rows only after Task 1 training and Task 4 forecasting run.
